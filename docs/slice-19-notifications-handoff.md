## What To Do

Add one private Notification Center that shows bounded, actionable notices generated by already-authoritative application transitions:

- Account lifecycle and security state;
- material Reference Event Plan review changes;
- Outpost Calendar plan changes;
- Membership, Position Verification, Permission Grant, and appointment decisions; and
- Operator Automation Alerts and existing review queues.

Target type: narrowed vertical slice. The user's category list is explicit; delivery is intentionally narrowed to in-app notifications plus the repository's already-required account emails so the slice can be implemented without inventing a new provider, preference center, or outbound-delivery policy.

## Why This Target

A single private notification model makes the existing workflows useful between visits while keeping authorization at the source. It avoids five unrelated alert implementations, prevents private values from leaking into email or public caches, and creates a stable seam for a later separately approved outbound-delivery slice.

## Assumptions To Record Before Coding

Add the missing notification terms to `CONTEXT.md` and write an ADR before adding the migration. Use these defaults unless newer product documentation explicitly overrides them:

- A `Notification` is a private, bounded, non-authoritative pointer to an existing application fact or required action. It is not the source of truth for Account state, event facts, Outpost intent, verification, permissions, or operations.
- Account and verification notices are owned by one Account.
- Calendar and Reference Event Plan notices are owned by one exact Outpost and are visible only while the viewer has current exact-scope private access. Per-Account read state may be stored separately; do not copy private content to every historical member.
- Operator notices remain accessible only to the active Operator Account and may reference an Automation Alert, Freshness Queue item, conflict, candidate, or other existing review object instead of duplicating that object's private payload.
- In-app notices are the canonical Slice 19 delivery surface. Existing verification, recovery, and Renewal Notice emails continue through their current fail-closed flows. No other email, SMS, or push delivery is added.
- Notifications use sanitized titles, reason codes, timestamps, and internal links. Sensitive notes, names, emails, source bodies, plan descriptions, and credentials stay at their authoritative private destination.

If any of these assumptions conflicts with newer product decisions, stop and document the contradiction before implementation.

## Inline Issue Brief

### What to build

Create one durable notification domain, event-to-notification projection, private API, and accessible UI surfaces that cover the five requested categories without weakening their existing authorization or lifecycle rules.

### Acceptance criteria

- [ ] An active ordinary Account can open a bounded Notification Center, filter by category/state, see an unread count, open the authoritative destination, and mark one or all visible notices read.
- [ ] Account notices cover actionable lifecycle/security state without duplicating or weakening Better Auth, the Ordinary Access Term, exact expiry, Renewal Notice delivery, session revocation, or deletion rules.
- [ ] A material Slice 18B Reference Event Plan change creates or coalesces an exact-Outpost event notice that links to the private comparison; repeated reads or maintenance retries do not create duplicates.
- [ ] Outpost Calendar create/update/cancel transitions create sanitized exact-Outpost notices that contain no roster, individual, youth, medical, transportation, contact, or plan-description data.
- [ ] Membership, Position Verification, Designated Pastor appointment, and Permission Grant decisions create recipient notices only after the authoritative transaction succeeds; self-claims still grant nothing.
- [ ] Grant revocation, Membership end, Account expiry, and Outpost-scope loss take effect on the next request. A stale notification ID cannot reveal the former scope or whether a private object exists.
- [ ] Operator notification summaries reuse or reference existing Automation Alerts and review queues, keep Operator Tenure attribution sanitized, and never expose the Operator identity or private object data to ordinary/public routes.
- [ ] Notification creation is transactionally coupled to the authoritative state change where practical, or uses a durable idempotent outbox/projection with documented replay behavior where coupling is not practical.
- [ ] Repeated triggers coalesce by a stable subject/reason key when the newest state supersedes older reminders; distinct audit-worthy transitions are not silently collapsed.
- [ ] Read/dismiss state is not treated as acknowledgement of an Automation Alert, acceptance of Reference Event facts, renewal, verification, permission, or any other domain decision.
- [ ] Permanent Account deletion removes Account-owned notifications and read state. Group-owned Calendar/Event history survives without retaining a deleted recipient identity; durable editorial references use only the existing `Deleted Account` rule where truly required.
- [ ] Every notification API is private and `no-store`, rejects cross-origin writes, derives principal/scope on the server, has bounded pagination, and is excluded from service-worker Cache Storage, public DTOs, public search, logs, and Operational Analytics payloads.
- [ ] Empty, loading, unread, all-read, inaccessible-target, and deleted-target UI states are keyboard accessible, screen-reader understandable, and responsive at 320, 390, 768, and 1280 CSS pixels.
- [ ] Existing Account email tests prove this slice did not start sending general notification emails or expose local preview behavior off exact loopback.
- [ ] Migration upgrade/fresh-install, scale, integration, lint, typecheck, build, browser, and privacy/cache gates pass, and current operations/QA/MVP documentation describes the final behavior honestly.

### Out of scope

- SMS, browser push, mobile push, webhooks, digest email, general event/calendar email, or a new delivery vendor.
- User-configurable channel/frequency preferences, quiet hours, reminder scheduling, or cross-device push subscriptions.
- Public notification counts, public Outpost activity, named member activity feeds, messaging, comments, or acknowledgements masquerading as domain actions.
- Attendance, RSVPs, organizer registration, youth data, or copied protected content.

## Decisions That Must Hold

- Claimed Position, Account type, and organizational relationship grant no notification access; exact current authorization is checked at read time. Source: ADRs 0003 and 0021.
- Automation remains bounded and human-accountable; a notice never publishes facts or resolves an alert. Source: ADRs 0004 and 0017.
- Ordinary authentication and Operator Access remain separate. Source: ADR 0018.
- Account expiry/deletion and Renewal Notice delivery rules are unchanged. Source: ADR 0019.
- Public Reference Calendar truth, private Outpost intent, and group-owned Calendar data remain separate. Source: ADRs 0022 and 0023.

## Implementation Guidance

- Write the ownership/delivery ADR first, then a forward-only migration with explicit owner constraints and indexes for bounded unread/category/time queries.
- Prefer stable subject IDs and reason codes over copied text. Render safe current labels at the authorized destination when possible.
- Generate a notification only from a successful authoritative transition. A retry must reuse the same idempotency/coalescing key.
- Reauthorize every Account-, Outpost-, and Operator-owned read. Never rely on notification ownership stored in client state.
- Do not place raw URLs from untrusted inputs in notification links. Route through allowlisted internal destinations and existing official external links.
- Keep unread/read writes small and replay-safe. Marking read is presentation state only.
- Use keyset pagination and server-enforced limits. Add the query shapes to the scale fixture before declaring completion.
