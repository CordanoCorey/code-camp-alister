# Cloudflare production deployment constraints

Research checked against current official Cloudflare documentation on 2026-08-12 and the lockfile-resolved source for `wrangler@4.122.0` and `@cloudflare/vite-plugin@1.52.0`. This note records only Slice 6 implementation constraints. Statements under **Confirmed** are documentation or package-source facts; statements under **Recommendation** are project-specific conclusions drawn from those facts.

## Vite, Workers environments, and D1 bindings

### Confirmed

- The Cloudflare Vite plugin builds the frontend assets and Worker together. A Vite build writes a flattened output Wrangler configuration that points to the built artifacts; subsequent `wrangler deploy` and `vite preview` commands automatically locate that output configuration. [Vite plugin migration reference](https://developers.cloudflare.com/workers/vite-plugin/reference/migrating-from-wrangler-dev/)
- With the Vite plugin, a Cloudflare environment is selected at **development/build time**, not deploy time. For example, PowerShell can run `$env:CLOUDFLARE_ENV = "production"; npx vite build`. Supplying `CLOUDFLARE_ENV` only to `wrangler deploy`, or using `wrangler deploy --env production` after a Vite build, does not select the environment in the generated output configuration. [Cloudflare environments for the Vite plugin](https://developers.cloudflare.com/workers/vite-plugin/reference/cloudflare-environments/)
- A named environment creates a distinct Worker named `<top-level-name>-<environment-name>`. `workers_dev = true` exposes that environment at an HTTPS URL such as `https://<worker>-production.<account-subdomain>.workers.dev`. [Wrangler environments](https://developers.cloudflare.com/workers/wrangler/environments/)
- Wrangler `vars` and resource bindings are non-inheritable: each named environment must declare its own values and bindings. This includes D1. A D1 binding needs `binding`, `database_name`, and the real `database_id`, and is exposed to code as `env.<binding>`. Default local development writes to local storage rather than the remote database. [Wrangler environments and non-inheritable keys](https://developers.cloudflare.com/workers/wrangler/environments/#non-inheritable-keys-and-environments), [D1 binding configuration](https://developers.cloudflare.com/workers/wrangler/configuration/#d1-databases), [Wrangler 4.122.0 environment types](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.122.0/packages/workers-utils/src/config/environment.ts)
- Cloudflare warns not to store sensitive values in `vars`. Local secrets belong in one of `.dev.vars` or `.env` (not both), and these files should be ignored by Git. Deployed Worker secrets can be set with `wrangler secret put`; doing so creates and immediately deploys a new Worker version. [Local secrets](https://developers.cloudflare.com/workers/wrangler/configuration/#local-development), [deployed secrets](https://developers.cloudflare.com/workers/configuration/secrets/)

### Recommendation

- Keep the top-level Wrangler configuration as local development and put the real D1 UUID only under `env.production.d1_databases`. Because `vars` are non-inheritable, omit `LOCAL_OPERATOR_PREVIEW` entirely from `env.production.vars`; do not set it to a false-looking string.
- Make the production build select the environment before Vite runs, then deploy the generated configuration without `--env`. A safe conceptual sequence is:

  ```powershell
  $env:CLOUDFLARE_ENV = "production"
  npm run build
  npx wrangler deploy
  ```

  An npm script should implement the same behavior in a Windows-safe way and must not imply that `wrangler deploy --env production` is sufficient for this Vite project.
- Keep Access issuer/audience settings server-only. Cloudflare documents them as Worker environment variables, but this project treats those identifiers as sensitive operational configuration; do not expose them through `VITE_*` or commit their values.

## D1 creation, migration, recovery, and analytics

### Confirmed

- `npx wrangler d1 create <NAME>` creates a remote database and returns its UUID/binding configuration. A Worker binding requires the immutable UUID. [D1 Wrangler commands](https://developers.cloudflare.com/d1/wrangler-commands/#d1-create), [D1 getting started](https://developers.cloudflare.com/d1/get-started/#3-bind-your-worker-to-your-d1-database)
- D1 commands defaulted to local operation beginning with Wrangler 3.33.0. Remote production operations must therefore say `--remote`; `--env production` can select the production binding for D1 control-plane commands. Unlike deploy/version commands, D1 commands in Wrangler 4.122.0 do not opt into the Vite-generated deploy-config redirect, and an explicit `--config` always selects that file. [D1 release notes](https://developers.cloudflare.com/d1/platform/release-notes/#2024-03-12), [D1 Wrangler commands](https://developers.cloudflare.com/d1/wrangler-commands/), [Wrangler 4.122.0 config resolution](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.122.0/packages/workers-utils/src/config/config-helpers.ts)
- `wrangler d1 migrations list <DB> --remote` lists unapplied remote migrations, and `wrangler d1 migrations apply <DB> --remote` applies them. Apply prompts in an interactive terminal, captures a backup after applying, rolls back a failing migration, and leaves earlier successful migrations applied. Cloudflare recommends using the database name rather than a mutable binding name when operating on migrations. [D1 migrations](https://developers.cloudflare.com/d1/reference/migrations/), [migration commands](https://developers.cloudflare.com/d1/wrangler-commands/#d1-migrations-apply), [Wrangler 4.122.0 migration apply](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.122.0/packages/wrangler/src/d1/migrations/apply.ts)
- A full remote SQL export uses `wrangler d1 export <DB> --remote --output=<outside-repo-path>.sql`; schema-only, data-only, and individual-table modes are available. However, export is unsupported for a database containing virtual tables, including FTS5, and a running export blocks other requests. Cloudflare's stated workaround is to delete the virtual table, export, and recreate it. [D1 import/export](https://developers.cloudflare.com/d1/best-practices/import-export-data/#export-an-existing-d1-database), [export limitations](https://developers.cloudflare.com/d1/best-practices/import-export-data/#known-limitations), [Wrangler 4.122.0 export command](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.122.0/packages/wrangler/src/d1/export.ts)
- Time Travel is always enabled on production-backend D1 databases and has no additional history/restore charge. Retrieve a bookmark with `wrangler d1 time-travel info <DB>` (optionally `--timestamp`), and restore with `wrangler d1 time-travel restore <DB> --bookmark=<BOOKMARK>` or `--timestamp=<TIME>`. A restore overwrites that database in place and cancels in-flight queries; the command returns the prior bookmark so the restore can be undone. Time Travel currently cannot clone/fork into a second database. [D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/), [Wrangler 4.122.0 restore command](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.122.0/packages/wrangler/src/d1/timeTravel/restore.ts)
- Free-plan Time Travel retains 7 days; Workers Paid retains 30 days. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/)
- D1 dashboard and GraphQL analytics expose read/write query counts, rows read/written, serialized response bytes, server-side query latency, and database size, retained for 31 days. `wrangler d1 insights` can rank queries by time, reads, writes, or count, but remains experimental. Insights captures SQL strings but not bound parameter values. [D1 metrics and analytics](https://developers.cloudflare.com/d1/observability/metrics-analytics/)

### Recommendation

- Require explicit targets in every script: `--local` for local work and `--config wrangler.jsonc --env production --remote` for production D1 work. The explicit source config matters because D1 commands do not consume the Vite-generated deploy config. Use the immutable production database name in operator-facing commands and confirm `wrangler d1 info`/migration state before writes.
- Capture the current Time Travel bookmark immediately before any future non-fresh migration. Do not describe that bookmark as an export or independent backup; it remains within the same Cloudflare account and database recovery system.
- Ranger Outpost Hub uses FTS virtual tables, so do not promise a routine full `wrangler d1 export`. Do not delete production FTS tables merely to make an export. Test whether a carefully scoped table export is useful, and otherwise treat Time Travel plus source-controlled forward migrations as the currently documented recovery path.
- Do not perform a Time Travel drill against production. The official service cannot restore a bookmark into a disposable target today. A disposable import drill would require a valid SQL export, which the FTS limitation may prevent.
- After smoke traffic, inspect D1 row metrics, latency, response bytes, and the FTS ordering query. Treat `d1 insights` output as experimental and operationally sensitive because it contains SQL structure even though it excludes bound values.

## Workers versions and rollback

### Confirmed

- Every Worker change creates a version containing bundled code, static assets, bindings, and compatibility settings. A deployment selects the version(s) serving traffic. `wrangler deploy` creates a version and deploys it to 100% in one step. D1/KV/R2/Durable Object data state is not part of a Worker version. [Versions and deployments](https://developers.cloudflare.com/workers/versions-and-deployments/)
- `wrangler versions list` and `wrangler deployments list` expose recent history. `wrangler rollback [VERSION_ID] --message <MESSAGE>` immediately creates a new deployment that sends 100% of traffic on all routes/domains to the selected version; without an ID, Wrangler 4.122.0 searches earlier deployments for the most recent version that had 100% traffic rather than blindly choosing the immediately preceding upload. [Wrangler Workers commands](https://developers.cloudflare.com/workers/wrangler/commands/workers/#rollback), [Wrangler 4.122.0 rollback implementation](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.122.0/packages/wrangler/src/versions/rollback/index.ts)
- Rollback is limited to the 100 most recently published versions. Connected data resources are not rolled back, and old code can fail if a database schema changed incompatibly. Rollback can also be blocked when a referenced bound resource no longer exists or certain binding/resource lifecycle changes occurred. [Worker rollbacks](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/)

### Recommendation

- Record the release commit SHA, deployment/version ID, and compatibility date together. Keep migrations forward-compatible with the immediately prior Worker version before running the rollback drill; a Worker rollback is not database recovery.
- Use `wrangler deployments list` before and after the drill, roll back to the known prior version with an explicit message, run read-only smoke checks, then deploy the reviewed release again and record the new deployment ID.

## Cloudflare Access on Operator paths

### Confirmed

- Cloudflare explicitly supports putting Access in front of a `workers.dev` URL. The Worker dashboard's **Enable Cloudflare Access** flow protects the Worker URL and can restrict it to specified emails. [Managing Access on `workers.dev`](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/#manage-access-to-workersdev)
- Current Access destinations can protect a Worker by ID (all routes) or a public hostname/path. The API reference says public destinations support a subdomain and path and take precedence over Worker-wide destinations, allowing policies for specific paths. [Access Applications API](https://developers.cloudflare.com/api/resources/zero_trust/subresources/access/subresources/applications/)
- Access path wildcards do not include their parent path: `host/operator/*` covers descendants but not `host/operator`. A hostname with an empty path or `/*` covers the hostname root and every path. More-specific application rules take precedence, and they do not inherit a less-specific rule when both exist. Query strings and fragments cannot participate in Access path matching. [Access application paths](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/app-paths/)
- Access is deny-by-default for a protected application. An Allow policy with an exact **Emails** selector can admit one address. Multiple Include rules are OR, Require rules are AND, and Cloudflare warns that **Include Everyone** or **Include Login Methods: One-time PIN** grants much broader access than an exact identity rule. [Access policies](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/)
- New Zero Trust organizations default to Cloudflare as an identity provider. Access also supports social/corporate OIDC and SAML providers, generic OIDC/SAML, and one-time PIN (OTP). Current OTP instructions say it may need to be explicitly added on newer organizations; an allowed address receives a single-use PIN that expires after 10 minutes. [Identity providers](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/), [OTP login](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/), [Cloudflare identity provider](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/cloudflare/)
- Access sends the application JWT in `Cf-Access-Jwt-Assertion`; browser requests also use a `CF_Authorization` cookie. The token's `iss` is the exact team-domain URL (`https://<team>.cloudflareaccess.com`), and `aud` contains the application's unique audience tag. The Worker must validate the RS256 signature against the team JWKS, issuer, audience, and time claims. Cloudflare rotates signing keys about every six weeks, retains the previous key for seven days, and recommends matching `kid` against the remote JWK set rather than hard-coding a certificate. [Application token claims](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/), [JWT validation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)
- Cloudflare's Worker-specific JWT example says that Access in front of a Worker does **not** remove the Worker's duty to validate `Cf-Access-Jwt-Assertion`. The application audience tag does not change unless the Access application is deleted/recreated. [JWT validation for Workers](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/#cloudflare-workers-example)

### Recommendation

- Use one self-hosted Access application with public path destinations for both the exact Operator HTML parent and its descendants, and for the Operator API descendants: `/operator`, `/operator/*`, and `/api/operator/*` (also protect exact `/api/operator` if it resolves). One application keeps one audience tag for Worker validation. Do **not** use the Worker-wide one-click gate because public pages and APIs must remain account-free.
- Attach one Allow policy whose only Include identity is the exact Operator email. Do not use a domain rule, `Everyone`, an unrestricted login-method rule, Bypass, or a service-token fallback. Select only the simplest login provider the Operator can control; OTP is adequate when deliberately configured, but an existing IdP may provide stronger MFA.
- Keep application-level Access and Worker-side JWT validation. Test missing/malformed assertions plus signature, issuer, audience, expiration, and not-before failures. Treat an absent Access issuer/audience configuration as deny, not as a local-preview signal.
- Verify path behavior in a logged-out browser before publishing. The narrative `workers.dev` guide documents only the whole-Worker dashboard shortcut, while selective Worker path destinations are documented most clearly in the newer API schema. Confirm the dashboard creates `public` path destinations (or use an approved API/IaC workflow) and inspect the resulting application before relying on it.

## Logs, metrics, and free-plan ceilings

### Confirmed

- Workers Logs stores invocation logs, custom logs, errors, and uncaught exceptions when observability is enabled in Wrangler. `head_sampling_rate` accepts 0 through 1 and defaults to 1. Workers Free includes 200,000 log events per day with 3-day retention; a single log is limited to 256 KB. [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)
- Automatic fetch invocation logs contain the request method and URL. They can be disabled with `observability.logs.invocation_logs = false` while custom `console.log` entries remain available in Workers Logs. [Workers Logs invocation logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/#invocation-logs), [Workers Logs custom logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/#custom-logs)
- `wrangler tail` provides non-stored real-time logs and supports method/status/search/sampling filters. High volume can cause sampling; at most 10 clients can view a Worker's real-time logs simultaneously. [Real-time logs](https://developers.cloudflare.com/workers/observability/logs/real-time-logs/)
- Built-in Worker metrics include request outcomes, invocation status, subrequests, CPU time, wall time, duration, and memory. Per-Worker metrics are retained for up to three months, and deployment markers help correlate regressions with releases. [Workers metrics and analytics](https://developers.cloudflare.com/workers/observability/metrics-and-analytics/)
- Current Workers Free limits include 100,000 dynamic Worker requests/day (reset at 00:00 UTC), 10 ms CPU/request, 128 MB memory, 50 external subrequests/request, 1,000 internal-service subrequests/request, 100 Workers, 20,000 static asset files/version, and 25 MiB per asset. Static asset requests are ordinarily free and unlimited. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)
- Current D1 Free allowances are 5 million rows read/day, 100,000 rows written/day, 5 GB total storage, 10 databases/account, 500 MB/database, 50 D1 queries per Worker invocation, and 7-day Time Travel. Daily read/write counters reset at 00:00 UTC; hitting a read/write ceiling causes D1 queries to fail until reset. [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/), [D1 limits](https://developers.cloudflare.com/d1/platform/limits/)
- Cloudflare Zero Trust Free is $0 for up to 50 users and lists standard log retention of up to 24 hours; one Operator is within that user cap. [Cloudflare Zero Trust pricing](https://www.cloudflare.com/plans/zero-trust-services/)

### Recommendation

- Enable production Workers Logs explicitly with a conservative nonzero `head_sampling_rate`; start high enough to capture the small beta's smoke traffic, then lower it if observed event volume approaches the Free allowance. Disable automatic invocation logs because their request URL can retain public search text. Persist only the custom entry containing route category, status, duration, and a generated correlation ID. Never emit Access assertions, Operator email, URL/query strings, request bodies, database rows, source notes, credentials, or account/resource IDs.
- Review usage before any plan change. Initial review thresholds should be deliberately below hard failure: investigate at roughly 70% of any daily request/row/log allowance or 70% of storage, and reassess indexes/caching/sampling before considering a paid plan. A Free launch is plausible at beta scale, not guaranteed indefinitely.

## Documentation conflicts and incomplete areas

- The D1 Time Travel introduction describes 30 days generically, but its plan-specific note and limits table say **7 days on Workers Free** and 30 days on Workers Paid. Use 7 days for this launch. [Time Travel notes](https://developers.cloudflare.com/d1/reference/time-travel/#notes), [D1 limits](https://developers.cloudflare.com/d1/platform/limits/)
- The D1 limits table says a Free database is limited to 500 MB, while the same page's generic FAQ says each database can store 10 GB. Use the explicit plan table's 500 MB Free limit. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/)
- Wrangler says migration apply captures a backup but current docs do not describe restoring that captured state into a different database. The documented recovery operation remains an in-place Time Travel restore; do not infer clone capability. [Migration commands](https://developers.cloudflare.com/d1/wrangler-commands/#d1-migrations-apply), [Time Travel notes](https://developers.cloudflare.com/d1/reference/time-travel/#notes)
- Cloudflare's identity-provider overview says OTP needs no configuration, while the dedicated current OTP page says newer Zero Trust organizations no longer add it automatically. Verify the actual account's login methods and explicitly add OTP if it is selected. [Identity providers](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/), [OTP setup](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/#set-up-otp)
- The narrative `workers.dev` guide describes the whole-Worker Access switch. The newer Access API schema documents path-specific public destinations taking precedence, but the public dashboard walkthrough does not show this selective `workers.dev` setup end-to-end. Treat dashboard confirmation and logged-out path tests as required launch evidence, not as assumed behavior. [Managing Access on `workers.dev`](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/#manage-access-to-workersdev), [Access Applications API](https://developers.cloudflare.com/api/resources/zero_trust/subresources/access/subresources/applications/)
