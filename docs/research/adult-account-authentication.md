# Adult account authentication on Cloudflare Workers and D1

Research date: 2026-08-13

## Scope and evidence boundary

This note evaluates Better Auth for the Slice 10 adult email/password account flow on the project's existing Cloudflare Worker and D1 stack. It covers the database adapter and schema, Worker routing, email verification, password recovery, session and origin security, rate limiting, email delivery boundaries, and Cloudflare compatibility. It does not select an email vendor or implement the separate adult-eligibility proof.

The candidate inspected was **Better Auth 1.6.27**, resolved through `opensrc` and checked against its versioned upstream source. The official Context7 snapshot available during research was `/better-auth/better-auth/v1.6.23`; it corroborated the public configuration surface but lagged the inspected package by four patch versions. Version-sensitive claims below therefore link to the [1.6.27 package source](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/better-auth/package.json) or other 1.6.27 files. The implementation pins exactly `better-auth@1.6.27`.

## Conclusion

Better Auth 1.6.27 is a viable, small authentication layer for Slice 10. It accepts a D1 binding directly, exposes a Fetch-native Worker handler, supplies email/password, verification, recovery, database sessions, and durable database rate limiting, and does not require a separate ORM. Use the core `better-auth` package directly; the additional `better-auth-cloudflare` integration is unnecessary for this slice.

The important qualifications are:

- Email-verification links are signed, expiring bearer JWTs, not database-consumed one-time tokens. Verification is state-idempotent, but the token can be replayed after success and any bearer can perform the first verification.
- Password-reset tokens are database-backed and consumed before changing the password in 1.6.27, but D1 concurrency must still be exercised in the Worker integration tests.
- Better Auth's in-memory rate limiter is unsuitable for Workers. Database storage is durable, but app-owned wrapper endpoints do not inherit the limiter when they call `auth.api` directly.
- The exact pinned bundle must be tested under workerd/Wrangler. Cloudflare does not certify Better Auth, and password hashing can make the Free-plan CPU budget a material constraint.

## Confirmed upstream facts

### Worker runtime and D1

Better Auth can receive a D1 binding as `database: env.DB`. Its Kysely adapter detects D1 and uses a D1-specific SQLite dialect; D1 batching substitutes for transaction-shaped adapter work because D1 does not expose interactive transactions. See the [official D1 announcement](https://better-auth.com/blog/1-5#cloudflare-d1-support), the [1.6.27 dialect selection](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/kysely-adapter/src/dialect.ts), and the [D1 dialect implementation](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/kysely-adapter/src/d1-sqlite-dialect.ts).

The request integration is standard Fetch: mount the configured auth base path for `GET` and `POST` and return `auth.handler(request)`. Server-side session reads use `auth.api.getSession({ headers: request.headers })`. The public [installation guide](https://better-auth.com/docs/installation) documents both interfaces.

Better Auth requires `AsyncLocalStorage`. Its Cloudflare instructions require either `nodejs_compat` or the narrower `nodejs_als` compatibility flag. The exact transitive password utility inspected exports its Node implementation for the `workerd` condition and uses `node:crypto` scrypt, so `nodejs_compat` is the safer explicit choice for this package version. Cloudflare documents the [compatibility flags](https://developers.cloudflare.com/workers/configuration/compatibility-flags/), [Node.js compatibility](https://developers.cloudflare.com/workers/runtime-apis/nodejs/), and [`node:crypto` support](https://developers.cloudflare.com/workers/runtime-apis/nodejs/crypto/).

Wrangler bundles Workers with esbuild. A successful TypeScript import is not enough because some Node APIs may only bundle as stubs; the exact production entry point needs a dry-run bundle and a workerd execution test. Cloudflare documents [Wrangler bundling](https://developers.cloudflare.com/workers/wrangler/bundling/) and Worker [bundle, startup, and CPU limits](https://developers.cloudflare.com/workers/platform/limits/).

### Schema and migrations

With its built-in Kysely adapter, Better Auth's CLI can generate SQL and can migrate databases it can reach. The D1 documentation instead shows programmatic `getMigrations`; it explicitly warns that a migration endpoint must be protected and removed after use. The relevant public reference is [Better Auth database concepts](https://better-auth.com/docs/concepts/database).

In 1.6.27 the core models are:

- `user`: unique email, verification state, name/image, and timestamps;
- `session`: unique token, expiry, user foreign key/index, IP address, user agent, and timestamps;
- `account`: provider/account identity, user foreign key/index, credential password hash and provider tokens;
- `verification`: indexed identifier, value, expiry, and timestamps; and
- `rateLimit`, when database rate-limit storage is enabled: unique key, count, and last-request time.

The authoritative field definitions are in the versioned [core table model source](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/core/src/db/get-tables.ts). The password hash belongs to `account`, not `user`. Model and field names can be customized, but generated SQL must match the runtime configuration exactly.

Cloudflare applies D1 migration files sequentially and records them in `d1_migrations`; a failing migration is rolled back without undoing earlier migration files. See [D1 migrations](https://developers.cloudflare.com/d1/reference/migrations/) and the [Wrangler D1 commands](https://developers.cloudflare.com/d1/wrangler-commands/).

### Email/password, verification, and recovery

`emailAndPassword.enabled` enables credential authentication. Better Auth defaults to an 8–128 character password range and scrypt hashing. Its signup route lowercases email before lookup/storage, and the schema makes email unique. See [email/password authentication](https://better-auth.com/docs/authentication/email-password), the [security reference](https://better-auth.com/docs/reference/security), and the [versioned signup route](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/better-auth/src/api/routes/sign-up.ts). This is lowercase normalization, not mailbox-provider-specific alias canonicalization.

With `emailAndPassword.requireEmailVerification: true`, signup does not create an authenticated browser session, and unverified email/password sign-in is rejected. Configure `emailVerification.sendVerificationEmail` and `sendOnSignUp`; `sendOnSignIn` can resend to an unverified user. Duplicate signup is enumeration-protected in this mode with a synthetic success response and simulated password work. The official [email documentation](https://better-auth.com/docs/concepts/email) and [enumeration-protection section](https://better-auth.com/docs/authentication/email-password#email-enumeration-protection) describe this behavior.

In 1.6.27, `createEmailVerificationToken` signs a JWT with HS256. Its payload contains the lowercased email, and its default lifetime is one hour. The token is carried in `/verify-email?token=...`; it is not inserted into the verification table and is not consumed. Once the user is already verified, reuse is a successful no-op and does not rerun `afterEmailVerification`. The exact behavior is visible in the [1.6.27 email-verification route](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/better-auth/src/api/routes/email-verification.ts).

Password-recovery requests return the same generic success for existing and missing users and simulate lookup work for a missing user. The default reset-token lifetime is one hour. In 1.6.27, the reset endpoint consumes the verification record before hashing or updating the password, so a racer or later reuse should fail. The [password route](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/better-auth/src/api/routes/password.ts) and the Kysely adapter's atomic [`consumeOne`](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/kysely-adapter/src/kysely-adapter.ts) are the version-sensitive evidence. Session revocation after reset is supported but disabled by default. The verification identifier can be stored hashed with `verification.storeIdentifier: "hashed"`; see the [verification options](https://better-auth.com/docs/reference/options#verification).

### Sessions, cookies, origin checks, and secrets

Sessions are database-backed by default. The default expiry is seven days and the default refresh interval (`updateAge`) is one day; sessions can be revoked. See [session management](https://better-auth.com/docs/concepts/session-management).

Auth cookies default to `HttpOnly`, `SameSite=Lax`, path `/`, and `Secure` when the effective base URL is HTTPS. Better Auth validates browser origins against `baseURL` and `trustedOrigins`, validates redirect/callback URLs, and uses Origin/Referer plus Fetch Metadata protections for CSRF. The project must not enable the options that disable origin or CSRF checks. A request with none of Origin, Referer, or Fetch Metadata is intentionally treated as a non-browser request and can pass these checks, which matters if the application intends to accept browser-only mutations. See the [security reference](https://better-auth.com/docs/reference/security) and [cookie concepts](https://better-auth.com/docs/concepts/cookies).

The auth secret must have at least 32 characters of high-entropy material; Better Auth supports multiple secrets for rotation. Cloudflare secret bindings are encrypted and should hold the auth secret and provider credentials, while a canonical URL, exact trusted origins, sender name/address, and provider selector can be ordinary Worker configuration. See the [Better Auth installation guide](https://better-auth.com/docs/installation) and [Cloudflare secrets documentation](https://developers.cloudflare.com/workers/configuration/secrets/).

### Durable abuse controls

Better Auth's default rate-limit storage is process memory and is explicitly unsuitable for serverless deployments. `rateLimit.storage: "database"` persists counters in the auth database and supports path-specific rules. The 1.6.27 database implementation uses an atomic consume/increment path when the adapter provides it; custom storage without `consume` falls back to a best-effort check then write. See [rate limiting](https://better-auth.com/docs/concepts/rate-limit) and the [1.6.27 limiter source](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/better-auth/src/api/rate-limiter/index.ts).

Only requests that pass through `auth.handler` run that middleware. Server calls through `auth.api` bypass the Better Auth limiter. Therefore, an app-owned `/api/account/signup` wrapper that validates eligibility and then calls `auth.api.signUpEmail` needs its own durable limiter, or it must forward the validated request through the handler without losing the eligibility gate.

On Cloudflare, set the trusted IP source explicitly to `cf-connecting-ip`. Better Auth derives a stored rate-limit key from client IP plus normalized route. It also records IP address and user agent on sessions by default. Disabling IP tracking also disables its per-IP limiter. These are security-data persistence choices, not logs, but they must be accounted for in the project's data-minimization policy. The exact address-resolution behavior is in the [1.6.27 IP utility](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/core/src/utils/ip.ts).

Cloudflare's native Rate Limiting binding is per Cloudflare location, eventually consistent, and deliberately permissive. It can add abuse friction but is not a substitute for a strict global/account lockout or the durable D1 control. See the [Cloudflare Rate Limiting binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/).

### Email callbacks, bearer links, caching, and logging

Verification and reset delivery callbacks receive `{ user, url, token }`; the completed URL contains the bearer token. Sending the link necessarily exposes it to the selected email provider and the recipient's mailbox. Better Auth recommends the runtime's background-task facility for serverless email work where the flow supports it; Cloudflare's equivalent is [`waitUntil`](https://developers.cloudflare.com/workers/runtime-apis/context/). Callback completion and error behavior must be verified per route before putting delivery in the background, because verification must not be presented as sent if the provider rejected it.

Reset and verification links place their bearer material in the URL. The application landing pages therefore need to avoid referrer, analytics, caching, and log leakage. In addition, the 1.6.27 signup source contains an info-level duplicate-signup message with the raw email address. Enabling info/debug logging would violate the project's no-raw-address logging requirement. Better Auth exposes [logger configuration](https://better-auth.com/docs/reference/options#logger); a disabled or rigorously redacted error-only logger is required.

## Slice 10 project decisions

The following are project choices based on the facts above, not upstream guarantees:

1. Pin exactly `better-auth@1.6.27`. Use native D1 support and do not add an ORM or `better-auth-cloudflare` for this slice. Re-research before changing the pin.
2. After pinning the package, generate its D1/Kysely SQL from the final model-name configuration, review it, and copy that exact schema into the existing forward-only `0011` Wrangler migration. Apply it through the repository's normal D1 migration workflow. Do not ship a runtime migration endpoint.
3. Add explicit `nodejs_compat` with the existing compatibility date. Gate the change on typecheck, tests, a Wrangler dry-run bundle, and workerd integration tests. Do not deploy from Slice 10.
4. Create the auth instance at the Worker boundary from typed bindings. Mount only the intended `GET`/`POST` auth path and keep app-owned eligibility/account routes separate. Return Better Auth responses through the existing Worker response policy.
5. Configure one canonical HTTPS `baseURL`, exact production `trustedOrigins`, no localhost production origin, no cross-subdomain cookie, and no disabled CSRF/origin checks. Reject startup/signup in production if the secret, canonical HTTPS origin, durable limiter, delivery provider, or sender configuration is absent. Do not expose any of these secrets through Vite.
6. Set `emailAndPassword.enabled: true`, `requireEmailVerification: true`, an explicit bounded reset expiry, and `revokeSessionsOnPasswordReset: true`. Preserve Better Auth's lowercase email uniqueness. Trim surrounding input in the application boundary, but do not invent provider-specific email canonicalization.
7. Set `emailVerification.sendOnSignUp: true` and `autoSignInAfterVerification: false`. Verification should activate the adult account/profile only through an idempotent, retryable transition. Because the auth user becomes verified before `afterEmailVerification` finishes and D1 has no cross-module interactive transaction, the application must repair “verified auth user, inactive/missing profile” rather than assume atomicity.
8. Set `verification.storeIdentifier: "hashed"`. Treat verification and reset URLs as bearer credentials. The provider-neutral email adapter should accept only destination plus a completed URL, never require callers to expose or persist the standalone token, and must not log destination, subject/body, URL, token, password, cookie, or session data.
9. Use Better Auth's D1 database limiter for `/api/auth/*`, with explicit rules for signup, sign-in, resend verification, forgot password, and reset. Add a durable application limiter for any `/api/account/*` wrapper that calls `auth.api`. Never use an isolate-local `Map` as the production control.
10. Keep session cookie caching off initially. Add `Cache-Control: private, no-store` to every `/api/auth/*` and `/api/account/*` response at the Worker route boundary, including errors and redirects; do not assume each library route sets it.
11. On verification/reset landing pages, send `Referrer-Policy: no-referrer` and `Cache-Control: private, no-store`, load no third-party assets or analytics, keep the token only in memory, and immediately remove it from the visible URL with `history.replaceState`. A link-revealing email preview is local-only, requires an explicit development flag and protected local sink, and must be rejected by production configuration.
12. Configure Better Auth logging as disabled or through a redacted error-only adapter. Application audit events may record coarse event kind, outcome, request ID, and timestamp, but never raw email, IP, user agent, bearer link/token, password, cookie, or session token.

## Required verification and remaining uncertainties

- Generate and inspect the exact 1.6.27 SQL before editing migration `0011`. Assert unique normalized email and session token, required foreign-key indexes, verification expiry/index behavior, and the `rateLimit` integer representation against D1.
- Exercise signup, duplicate signup, unverified sign-in, resend, verification replay, reset enumeration, reset expiry/replay/racing requests, password change, and session revocation in Miniflare/workerd against the real migration. Unit tests alone cannot establish D1 concurrency behavior.
- Prove that the adult eligibility grant is consumed once and before auth-user creation. Prove that activation repairs a verified user whose profile transition failed. Better Auth does not make those application records atomic with its own operations.
- Measure the dry-run gzip/uncompressed bundle, startup time, and password-hash CPU in workerd and the intended Cloudflare plan. Cloudflare's published limits make Free-plan CPU headroom uncertain; no production compatibility claim is justified until measured.
- Decide whether persisting raw session IP/user-agent values and an IP-derived D1 rate-limit key is acceptable. If not, use a tested session database hook and keyed-hash custom durable limiter; do not disable IP tracking without replacing the abuse control.
- Verify email callback failure and retry behavior with the selected provider. The research establishes the interface and leakage boundary, not deliverability or provider-specific timeout/idempotency semantics.
- Treat email verification as an expiring signed identity assertion with state-based idempotence, not a one-time token. If the product requires cryptographic single use, Better Auth's built-in 1.6.27 verification flow does not meet that stronger requirement without a project-owned consumption record.
- Re-run source review and all compatibility checks for any Better Auth upgrade. Context7's available snapshot was 1.6.23, so the exact 1.6.27 source remains the controlling evidence for this implementation.

## Slice 11 research update: expiration, revocation, and irreversible deletion

Research update: 2026-08-13

This section answers the Slice 11 questions against the pinned `better-auth@1.6.27` source, the current official Better Auth 1.6 documentation, Cloudflare D1 documentation, Resend documentation, and the repository's migration 0011. Context7 still exposes Better Auth 1.6.23 rather than 1.6.27, so the versioned 1.6.27 source remains controlling when the two differ.

### User deletion and the rows it does and does not remove

Better Auth documents a hard-delete user facility, but its self-service `/delete-user` route is disabled unless `user.deleteUser.enabled` is set. It requires the signed-in user's password, a fresh session, or a verified deletion token. That product flow does not fit scheduled lifecycle deletion, so Slice 11 should leave it disabled. The admin plugin also has `removeUser`, but adding an authenticated admin HTTP surface and plugin schema solely for maintenance is unnecessary. See [Better Auth user deletion](https://better-auth.com/docs/concepts/users-accounts#delete-user), [the admin plugin](https://better-auth.com/docs/plugins/admin#remove-user), and the pinned [delete-user route](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/better-auth/src/api/routes/update-user.ts).

In 1.6.27, the internal adapter's `deleteUser(userId)` performs separate awaited operations: remove secondary-storage sessions, remove database sessions, delete all `account` rows for the user, and then delete the `user`. It does **not** delete `verification` rows. The public self-service route calls that helper and then calls session deletion again. These are sequential adapter operations, not one D1 transaction. With migration 0011's eligibility no-delete trigger, the final user deletion can fail after the earlier session/account deletes have committed, leaving a partially stripped but still identifiable user. `internalAdapter` is an implementation surface rather than a documented stable maintenance API, so calling it from lifecycle maintenance would couple the app to the exact pin and still would not satisfy full deletion by itself. See the pinned [internal adapter](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/better-auth/src/db/internal-adapter.ts) and [hooked delete implementation](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/better-auth/src/db/with-hooks.ts).

Migration 0011 gives both `session.userId` and `account.userId` `ON DELETE CASCADE`, which matches Better Auth's generated relational model: deleting `user` removes database sessions and credential/provider accounts, including the credential password hash. D1 enforces foreign keys by default and defines `CASCADE` as deleting associated child rows. See [`migrations/0011_ordinary_adult_accounts.sql`](../../migrations/0011_ordinary_adult_accounts.sql), the official [Better Auth core schema](https://better-auth.com/docs/concepts/database#core-schema), and [D1 foreign-key actions](https://developers.cloudflare.com/d1/sql-api/foreign-keys/#foreign-key-actions).

That cascade is necessary but is not presently sufficient:

- Better Auth's `verification` table has no user foreign key. In this configuration password-reset records store the auth user ID as their `value`, so deleting `user` directly can leave reset material unless the guarded transition explicitly deletes matching verification rows. Email-verification links are signed JWTs and have no verification row to cascade.
- `local_auth_email_previews`, `ordinary_account_profiles`, the consumed eligibility challenge, and `ordinary_adult_eligibility` reference the auth user with cascades, but migration 0011's `ordinary_adult_eligibility_no_delete` trigger aborts even cascaded deletion. Migration 0012 therefore needs the narrowly guarded deletion mechanism required by the handoff, plus real-D1 tests proving the whole graph disappears.
- `rateLimit` has no user foreign key. Its keys are request/IP-derived in the current Better Auth configuration rather than durable user-profile rows, so it cannot be assumed to cascade or to be safely discoverable by user ID. The deletion verification must enumerate every table that can contain the auth user ID or account-private material rather than relying on the word "user" in a table name.

The safe Slice 11 conclusion is an application-owned, guarded D1 deletion transition for this known pinned schema: explicitly clear user-keyed verification/application material and delete the `user` so declared cascades clear account, session, profile, preview, and eligibility rows. It must verify the due lifecycle state/version inside the SQL write path and assert absence afterward. This is not a license to delete only the application profile or only the credential account; all Better Auth and application rows must be covered, and a repeat must be a no-op.

Deleting the rows individually has narrower effects that are unsafe as a substitute: deleting only `account` removes the password/provider credentials but leaves user PII and sessions; deleting only `session` revokes those sessions but leaves the account; deleting a password-reset `verification` row cancels that database-backed challenge but does not revoke a separately issued email-verification JWT. After full user deletion, such a JWT still cannot recreate the missing user because verification performs a user lookup rather than user creation.

### Session revocation and expired-account enforcement

Better Auth documents `revokeSession`, `revokeOtherSessions`, and `revokeSessions`; the latter is a current-user operation authenticated by that user's headers. The admin plugin exposes revoke-by-user, while the pinned internal adapter has `deleteUserSessions(userId)`. The current project stores sessions only in D1, has no secondary session store, has `preserveSessionInDatabase` off, and does not enable cookie caching. Therefore an idempotent `DELETE FROM session WHERE userId = ?` inside the lifecycle transition revokes every current session immediately at the server's source of truth. If cookie caching is ever enabled, Better Auth warns that a revoked session may remain usable until the cookie cache expires, so Slice 11 should keep it off. See [session revocation and cookie-cache caveats](https://better-auth.com/docs/concepts/session-management#session-management) and the pinned [session deletion implementation](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/better-auth/src/db/internal-adapter.ts).

Revocation alone is race-prone: a concurrent sign-in can create a new session after maintenance deletes the old rows. Better Auth database hooks support `session.create.before` and `session.update.before`; returning `false` aborts the write, and throwing an `APIError` can fail it explicitly. In 1.6.27, every core path inspected that creates a persisted session calls `internalAdapter.createSession`, which runs the configured create hooks. Slice 11 should use a create-before hook that loads the lifecycle by `session.userId` and fails closed when access is expired or the lifecycle check fails. It also needs an update-before hook, because Better Auth's rolling session refresh updates `expiresAt` after `updateAge`. See [database hooks](https://better-auth.com/docs/concepts/database#database-hooks), the pinned [hook runner](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/better-auth/src/db/with-hooks.ts), and the pinned [session creation/refresh source](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/better-auth/src/api/routes/session.ts).

There is no documented v1.6 NextAuth-style general session callback that serves as an issuance-and-validation gate. `customSession` shapes returned session data; it is not the lifecycle authorization boundary. Better Auth request hooks are route-specific, so they can add defense in depth but do not replace the database session hook plus application authorization. See [Better Auth request hooks](https://better-auth.com/docs/concepts/hooks#before-hooks) and [custom session responses](https://better-auth.com/docs/concepts/session-management#customizing-session-response).

The create hook's lifecycle `SELECT` and Better Auth's later session `INSERT` are separate D1 calls, so another request can interleave and the hook alone is not an atomic exact-boundary invariant. A database trigger/same-statement guard should reject session insertion when the lifecycle is already expired if the implementation must prove that no row can be inserted across that edge. Regardless, the private-route due-time check remains mandatory: even a session row created by a boundary racer grants no private capability.

Hooks are only one layer. An existing session can be read between refreshes without a create or update hook. Every ordinary private route must therefore pass through one server-side authorization boundary that loads the authenticated session and the current lifecycle, denies ordinary private access at or after `access_due_at`, and may opportunistically delete the user's sessions. Public routes and the separate Operator boundary must not use this ordinary lifecycle check. Expiry maintenance remains necessary for autonomous revocation, but correctness cannot depend on the Cron having run at the exact due instant.

### Can a callback recreate or extend an expired session?

Yes, unless Slice 11 guards every session create/update path:

- Email/password sign-in creates a new session after credential and verification checks. A session-create hook is the last shared Better Auth database boundary that can reject an expired user. See the pinned [sign-in route](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/better-auth/src/api/routes/sign-in.ts).
- Ordinary email verification would create a session when `autoSignInAfterVerification` is true. The project already sets it to `false`, so the normal Slice 10 verification callback does not auto-sign in. The pinned change-email verification paths can also create a session, but change-email is not enabled and the Worker allowlist does not expose its initiating route. The create hook should still be authoritative so a later route/configuration change cannot bypass expiry. See the pinned [email-verification route](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/better-auth/src/api/routes/email-verification.ts).
- Password reset does not create a session in 1.6.27 and the project has `revokeSessionsOnPasswordReset: true`, but it also does not grant ordinary private access. See the pinned [password-reset route](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/better-auth/src/api/routes/password.ts).
- `getSession` performs a rolling update from the current time plus `expiresIn` when `updateAge` is reached. Without the lifecycle-aware update hook or `disableSessionRefresh`, a session that survives the due instant can be extended. Even with the hook, the private-route lifecycle check is needed on reads that are not yet due for refresh. Better Auth documents this rolling behavior in [session expiration](https://better-auth.com/docs/concepts/session-management#session-expiration).
- The password-change `revokeOtherSessions` path deletes all sessions and creates a replacement session. It is not in the project's auth-route allowlist, but again is covered by the create hook if later exposed.

The lifecycle due time should not be copied into Better Auth session expiry as the sole control. The seven-day session and one-year ordinary access term are different concepts: a session may expire earlier, and renewal extends account access without granting a new session.

### D1 atomicity, concurrency, and retries

D1's binding runs statements in auto-commit mode. `D1Database.batch()` is the supported atomic multi-statement primitive: statements execute sequentially and non-concurrently, and a failure aborts or rolls back the whole batch. D1 does not expose an interactive transaction in which application code can read a result and then decide later statements; Better Auth's pinned D1 Kysely dialect explicitly throws for begin/commit/rollback and sets adapter transactions to `undefined`. See the official [D1 `batch()` contract](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch), the pinned [D1 dialect](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/kysely-adapter/src/d1-sqlite-dialect.ts), and the pinned [dialect selection](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/kysely-adapter/src/dialect.ts).

An individual D1 database processes queries one at a time, but that does not make a read/check followed by a later write atomic: another request can be queued between the two statements. Renewal, notice claiming, expiry, and deletion therefore need single-statement conditional writes or a `batch()` whose destructive statements each carry the lifecycle identity/version/due guard (with constraints/triggers as a backstop). D1 can queue concurrent requests and return `overloaded` when the queue fills, so maintenance must remain bounded and indexed. See [D1 concurrency and throughput](https://developers.cloudflare.com/d1/reference/faq/#concurrency-and-throughput).

Cloudflare automatically retries retryable read-only queries up to two times, not writes. Its write-retry guidance calls for application-owned exponential backoff with jitter for classified transient errors. Lifecycle write retries are safe only when the SQL transition is idempotent and rechecks its version/state. If read replication is enabled later, due-state write decisions should start on the primary or maintain a D1 Session bookmark; unconstrained replicas may lag. See [D1 retry guidance](https://developers.cloudflare.com/d1/best-practices/retry-queries/) and [D1 read-replication consistency](https://developers.cloudflare.com/d1/best-practices/read-replication/).

### Warning-email retry and idempotency

Better Auth email callbacks supply an application delivery callback; they do not provide a durable outbox, a lifecycle-warning type, retry scheduling, or provider idempotency. The pinned routes invoke the callback once for that request, sometimes through `runInBackgroundOrAwait`, and do not persist a send attempt. Slice 11's autonomous warning must therefore be application-owned rather than disguised as a Better Auth verification/recovery email callback. See the pinned [verification-email path](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/better-auth/src/api/routes/email-verification.ts), [signup path](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/better-auth/src/api/routes/sign-up.ts), and [password-recovery path](https://github.com/better-auth/better-auth/blob/v1.6.27/packages/better-auth/src/api/routes/password.ts).

The configured provider, Resend, supports an `Idempotency-Key` header on `POST /emails`. Reusing a key with the same payload within 24 hours returns the original result without sending another email; the key is limited to 256 characters and expires after 24 hours. Concurrent identical requests can return `409 concurrent_idempotent_requests` and are safe to retry later; a reused key with a different payload returns a non-retryable `409 invalid_idempotent_request`. Resend identifies rate limiting with 429 and recommends later retry for 500 errors. See [Resend idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys), the [send-email API](https://resend.com/docs/api-reference/emails/send-email), and [error semantics](https://resend.com/docs/api-reference/errors).

For each lifecycle term, maintenance should durably claim one non-PII attempt/idempotency key before network I/O, resolve the destination just-in-time from `user`, send the exact same payload/key on ambiguous or transient retries, and mark `warning_delivered_at` only after a provider-accepted success response. The stored provider response may include the provider message ID and coarse outcome, but not destination, subject/body, link, or credentials. Resend distinguishes `email.sent` (the API request succeeded and Resend will attempt delivery) from `email.delivered` (the recipient mail server accepted the message). The handoff explicitly defines confirmation as provider acceptance, so a successful send response/provider message ID is the Slice 11 deadline point; webhook-confirmed mail-server delivery would be a materially different requirement. See [Resend event semantics](https://resend.com/docs/webhooks/event-types).

Because Resend retains idempotency keys for only 24 hours, it is not an unlimited exactly-once guarantee. Keep bounded retries for an ambiguous acceptance inside that window where practical; after permanent/repeated failure, coalesce a private alert and do not set the delivery or deletion timestamps. Persisting the term claim in D1 prevents maintenance overlap and notice storms even after the provider deduplication window closes.

### Slice 11 implementation consequences

1. Leave Better Auth's public self-service delete-user endpoint and the admin plugin disabled.
2. Add lifecycle-aware `session.create.before` and `session.update.before` hooks, keep cookie caching off, and enforce lifecycle state again at the shared ordinary-private authorization boundary.
3. Expiration maintenance should conditionally mark the lifecycle expired and delete all D1 session rows for that auth user idempotently; route enforcement supplies the exact-boundary guarantee even if maintenance is delayed.
4. Permanent deletion must be one guarded D1 transition for the pinned schema, not only `internalAdapter.deleteUser()`: remove reset/verification material and application-private rows, delete the user so declared cascades remove sessions/accounts/profile data, and assert nothing searchable remains. Migration 0012 must safely overcome the current eligibility no-delete trigger only inside that transition.
5. Warning delivery needs a D1 outbox/attempt record plus a deterministic per-term Resend key, bounded classified retries, and a fail-closed alert path. Do not start the deletion clock before provider acceptance.
6. Test sign-in, verification, password reset, get-session refresh, password change if ever exposed, overlapping expiration/renewal, and deletion against the real Worker/D1 adapter. The required property is that no Better Auth callback or rolling refresh can create or extend an expired ordinary session.
