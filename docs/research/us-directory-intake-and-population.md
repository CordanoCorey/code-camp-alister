# Cloudflare constraints for U.S. directory intake and population

**Research date:** 2026-08-13

**Versions inspected:** `wrangler@4.122.0`, `@cloudflare/workers-types@5.20260812.1`

**Source policy:** Official Cloudflare documentation and version-matched Cloudflare package source only.

## Material conclusions

### Confirmed platform facts

- **Turnstile is the available no-cost human-verification seam.** Its Free plan supports production use, up to 20 widgets, ten configured hostnames per widget, and unlimited challenges. Siteverify is still mandatory; a client-side success alone protects nothing. ([Turnstile plans](https://developers.cloudflare.com/turnstile/plans/), [server-side validation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/))
- The Worker must `POST` the private secret and client token to `https://challenges.cloudflare.com/turnstile/v0/siteverify`. Tokens are at most 2,048 characters, expire after 300 seconds, and are single-use; an expired or replayed token fails, commonly with `timeout-or-duplicate`. A successful response also returns the challenge `hostname` and `action`. Accept only `success === true`, the exact intake action, and a hostname in an explicit deployment allowlist. ([Siteverify](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/), [widget action](https://developers.cloudflare.com/turnstile/get-started/client-side-rendering/widget-configurations/), [hostname management](https://developers.cloudflare.com/turnstile/additional-configuration/hostname-management/))
- Siteverify's optional `idempotency_key` is an application-generated UUID for safely retrying a validation request. Cloudflare does not document its retention, payload-conflict behavior, or use as application-level idempotency. Reuse one UUID only for a transport retry of the **same token**. Database duplicate handling and manifest checksum idempotency remain separate concerns. ([Siteverify request fields](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/))
- Official dummy keys cover always-pass, always-fail, forced-interactive, and already-spent behavior. Test keys work on local hostnames; test secrets accept only dummy tokens, while production secrets reject them. Provider-key tests should cover integration pass/fail/spent behavior, while deterministic Siteverify stubs should cover exact action, hostname, timeout, non-2xx, and malformed-response branches. ([Turnstile testing](https://developers.cloudflare.com/turnstile/troubleshooting/testing/))
- `db.batch()` runs prepared statements sequentially as a transaction; a failed statement aborts or rolls back the sequence. Per-query D1 ceilings still apply to every statement: 100 bound parameters, 100 KB SQL, 2 MB maximum string/BLOB/row, and 30 seconds. The 30-second ceiling also applies to the entire batch call. D1 publishes no separate batch statement-count maximum. ([D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch), [D1 limits](https://developers.cloudflare.com/d1/platform/limits/))
- On Workers Free, D1 permits 50 queries per Worker invocation, a 500 MB database, 5 million rows read/day, and 100,000 rows written/day. Inserts, updates, deletes, indexes, Wrangler commands, and imports consume row usage. The general Workers limit permits a 100 MB incoming body on a Free Cloudflare zone, but that is an infrastructure ceiling, not a suitable form limit; the intake endpoint must enforce its own much smaller byte limit before JSON parsing or D1 work. ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/), [Workers limits](https://developers.cloudflare.com/workers/platform/limits/))
- `d1 execute --file` accepts SQL text, not a raw SQLite file, and remote imports are limited to 5 GB. Cloudflare recommends splitting oversized individual `INSERT` statements, and the remote import API blocks the database for the import's duration. That facility is appropriate for controlled SQL migration/import work, not for reviewed directory manifests whose staging must enforce Operator tenure, provenance, audit, and draft-only invariants. ([D1 import/export](https://developers.cloudflare.com/d1/best-practices/import-export-data/), [D1 import API](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/import/))

### Safe local and remote operation

- The lockfile-resolved Wrangler source makes `d1 execute` local unless `--remote` or remote `--preview` is explicit, rejects simultaneous `--local --remote`, requires `--local` for `--persist-to`, batches local SQL statements, and warns that a remote file import makes D1 unavailable while it runs. The public documentation has had conflicting wording about an omitted target, so scripts must never rely on the default. ([Wrangler 4.122.0 `execute.ts`](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.122.0/packages/wrangler/src/d1/execute.ts), [D1 CLI reference](https://developers.cloudflare.com/d1/wrangler-commands/), [local D1 development](https://developers.cloudflare.com/d1/best-practices/local-development/))
- Local staging/tests should say `--local` and use an isolated `--persist-to` directory where destructive or partial-failure scenarios run. A separately named production operation must say `--config wrangler.jsonc --env production --remote`, resolve the non-placeholder production binding, display/verify the intended database identity, and retain the interactive confirmation. Do not use `--yes`, `--json`, or non-interactive execution as a substitute for a project-level production confirmation because Wrangler only prompts for a remote file import in an interactive terminal. ([Wrangler 4.122.0 `execute.ts`](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.122.0/packages/wrangler/src/d1/execute.ts), [D1 CLI reference](https://developers.cloudflare.com/d1/wrangler-commands/))
- Do not stage a population manifest by generating raw SQL for `d1 execute`. Validate and checksum the human-readable manifest first, then invoke the canonical application staging path so the whole logical candidate/batch write uses bound statements and a failing `db.batch()`. One invalid candidate must fail before mutation; one SQL failure must roll back the entire staged batch. Canonical conversion remains an active-Tenure action that creates drafts only.

### Plan-dependent rate limiting

- The repository's selected launch target is Workers Free on a provider `workers.dev` hostname. Cloudflare's Workers Rate Limiting binding is GA, supported by this pinned Wrangler (minimum documented version is 4.36), and accepts only 10- or 60-second windows. Its counters are per Cloudflare location, permissive/eventually consistent, and unsuitable for exact accounting. Cloudflare also advises against using shared IP addresses as limiter keys. ([Workers Rate Limiting binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/), [GA notice](https://developers.cloudflare.com/changelog/post/2025-09-19-ratelimit-workers-ga/), [Wrangler 4.122.0 rate-limit schema](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.122.0/packages/workers-utils/src/config/environment.ts))
- **Unconfirmed for the selected plan:** current binding and Workers pricing documentation does not explicitly promise that the Workers Rate Limiting binding has no separate charge or is entitled on Workers Free. Do not make production intake depend on that unverified entitlement until the real account accepts a deployed binding and the dashboard confirms no paid-plan change.
- A separate zone-level WAF capability explicitly includes one limited rate-limiting rule on the Cloudflare Free plan: path/verified-bot matching, IP counting, and a 10-second window/mitigation. It is plan- and routing-dependent and does not establish protection for the planned provider `workers.dev` hostname. It can be defense in depth after a custom Cloudflare zone is actually in scope, not a present launch prerequisite. ([WAF rate-limiting availability](https://developers.cloudflare.com/waf/rate-limiting-rules/))

## Fail-closed production guidance

Production database intake is enabled only when all of the following are present and deployment-tested: a real Free Turnstile widget restricted to the production hostname, a Worker-only production secret, a public sitekey, a nonempty exact hostname allowlist, and the fixed intake action. Missing configuration, missing/oversized token, Siteverify timeout/network/non-2xx/malformed JSON, `success: false`, action mismatch, hostname mismatch, and replay all mean **no D1 write**. Return a generic retry/fallback message, reset the widget for a fresh token, and keep public browsing and the email/copy fallback available.

The Siteverify call should have a short timeout. A successful challenge followed by a failed D1 write does not authorize replay: the client must obtain a fresh token, while the private duplicate fingerprint supplies a non-enumerating accepted-duplicate result if the first write actually committed. Never store the challenge token, Siteverify payload, idempotency UUID, IP, or rate-limit key in D1, audit snapshots, logs, or public responses. The optional `remoteip` field is not required by Siteverify and can be omitted to avoid introducing IP handling.

Turnstile is the confirmed no-cost production abuse control for this launch; origin/content-type/body-size checks, validation, honeypot and timing checks are additional application controls. A rate limiter is defense in depth, not a replacement for Siteverify. Until production keys and exact hostname/action validation are evidenced, keep database intake disabled and describe the existing email/copy path honestly.
