# Cloudflare automated-maintenance runtime constraints

**Research date:** 2026-08-13

**Versions inspected:** `wrangler@4.122.0`, `@cloudflare/vite-plugin@1.52.0`, `@cloudflare/workers-types@5.20260812.1`

**Source policy:** Current official Cloudflare documentation and lockfile-resolved Cloudflare package source only. Local counts below are planning inputs, not deployed evidence.

## Production schedule decision

Use one production-only dispatcher Cron at `7,37 * * * *` (every 30 minutes UTC), with D1 deciding which jobs and targets are due. Put the trigger only at `env.production.triggers.crons`; use an explicit empty Cron array in any non-production configuration that can be deployed remotely. Cloudflare supports five-field expressions at one-minute resolution and environment-specific triggers, and documents no separate Free/Paid cadence floor. The platform allows 5 Cron Triggers per Free account and 250 per Paid account, so one dispatcher avoids both trigger sprawl and per-rule deployment coupling. ([Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/), [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Wrangler 4.122.0 environment validation](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.122.0/packages/workers-utils/src/config/validation.ts))

The cadence is capacity-driven. The existing local developer D1 contained 139 content records and 38 deduplicated Source Documents when inspected; the repository scale target is 20,000 Outposts. At 48 invocations/day, an application cap of 16 due monitors per run provides 23,040 check slots per 30 days. Capping each monitor at the initial request plus at most one same-policy validated redirect consumes at most 32 of the Free plan's 50 external subrequests and leaves 18 as safety margin. This is enough for the deliberately conservative planning case of one approved monthly monitor per scale-fixture Outpost, but not for 20,000 weekly monitors. The scale check must substitute its measured deduplicated-source count and fail or report a capacity gap if chosen monitor intervals exceed this budget. Source monitoring remains default-off and gradual; deterministic lifecycle work uses indexed D1 batches rather than one subrequest per Outpost.

The half-hour cadence also bounds a due transition's normal scheduling delay below 30 minutes and uses only 48 of the Free plan's 100,000 daily Worker requests. It does **not** prove the workload fits the Free plan's 10 ms Cron CPU ceiling. Paid Cron invocations scheduled more often than hourly receive 30 seconds of CPU, while hourly-or-less-frequent Paid Cron invocations receive up to 15 minutes; both plans have a 15-minute Cron wall-time ceiling. Production activation therefore requires deployed CPU, D1 row, byte, and duration evidence with the final batch sizes. If the Free ceiling is reached, defer/back off due work and pause source monitors; do not tighten the Cron loop or bypass the cap. ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/))

## Configuration, handler, and local testing

- Export a module Worker with both existing `fetch()` behavior and `scheduled(controller, env, ctx)`. `controller.cron` is the exact configured string and `controller.scheduledTime` is the intended UTC epoch time. Pass the bounded dispatcher promise to `ctx.waitUntil()`. For a scheduled handler, Cloudflare also waits for a returned promise; a rejected `waitUntil()` promise is recorded as the Cron outcome, which makes a sanitized terminal dispatcher failure observable. ([Scheduled handler](https://developers.cloudflare.com/workers/runtime-apis/handlers/scheduled/), [`ctx.waitUntil()`](https://developers.cloudflare.com/workers/runtime-apis/context/))
- Cron configuration is deploy state, not just code. Adding, changing, or removing a trigger can take up to 15 minutes to propagate. With Wrangler, a defined Cron array replaces all schedules, `[]` removes them, and an undefined array leaves the already-deployed schedules untouched; merely omitting or commenting out the key does not disable an old trigger. Because this repository's Vite environment is selected at build time, production validation must inspect the generated production configuration and the deployed trigger; a source `wrangler.jsonc` assertion alone cannot prove activation. ([Cron deployment behavior](https://developers.cloudflare.com/workers/configuration/cron-triggers/), [Wrangler 4.122.0 schedule deployment](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.122.0/packages/deploy-helpers/src/triggers/deploy.ts), [Vite Cloudflare environments](https://developers.cloudflare.com/workers/vite-plugin/reference/cloudflare-environments/))
- Local development does not fire schedules automatically. Current public docs show the legacy-compatible `/cdn-cgi/handler/scheduled?format=json&cron=...&time=...` route. The pinned Vite/Wrangler source identifies `/cdn-cgi/local/scheduled` as the canonical local route and transparently rewrites the older handler route; use the canonical route in the separately named local command and pass explicit `cron`, `time`, and `format=json`. Wrangler 4.122.0 still retains the separate legacy `--test-scheduled` plus `/__scheduled` mode, but operations and tests should use one pinned mode rather than mixing route contracts. Direct unit tests may invoke the exported handler with an injected clock and a captured `waitUntil` promise. ([local Cron testing](https://developers.cloudflare.com/workers/configuration/cron-triggers/#test-cron-triggers-locally), [Wrangler 4.122.0 local warning](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.122.0/packages/wrangler/src/dev/start-dev.ts), [Wrangler 4.122.0 legacy flag](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.122.0/packages/wrangler/src/dev.ts), [Vite plugin 1.52 route rewrite](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.122.0/packages/vite-plugin-cloudflare/src/plugins/trigger-handlers.ts), [Wrangler 4.122.0 test harness](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.122.0/packages/wrangler/src/api/test-harness.ts))

## Runtime and D1 budgets

| Constraint | Free | Paid | Slice 9 consequence |
| --- | ---: | ---: | --- |
| Cron triggers/account | 5 | 250 | Configure one dispatcher. |
| Cron CPU | 10 ms | 30 s for intervals `< 1h`; 15 min for intervals `>= 1h` | Keep rule evaluation, hashing, and result shaping small; deployed measurement gates activation. |
| Cron wall time | 15 min | 15 min | Enforce a shorter application deadline and checkpoint before it. |
| External subrequests/invocation | 50 | 10,000 by default, configurable up to 10M | Cap source targets and redirect hops; each redirect-chain request counts. |
| Internal-service subrequests/invocation | 1,000 | Matches configured subrequest limit | D1 calls remain bounded even though they do not consume the Free external-50 pool. |
| Simultaneous outgoing connections | 6 | 6 | Process sequentially or with deliberately small concurrency and always consume/cancel bodies. |
| D1 queries/invocation | 50 | 1,000 | Use set-based due claims and `db.batch()`, not per-row read/write fan-out. |
| D1 query / whole-batch duration | 30 s | 30 s | Keep each claim/action transaction small and checkpointed. |
| D1 included rows | 5M read + 100K written/day | 25B read + 50M written/month, then billed | Index every due/lease/backoff queue; count index writes and retained observations. Free overage fails until reset at 00:00 UTC rather than degrading to unlimited work. |
| D1 database size | 500 MB | 10 GB | Prune routine unchanged observations only under the documented audit-retention rules. |

Cloudflare counts each redirect hop as a subrequest. D1 allows no more than six simultaneous connections from an invocation, is single-threaded per database, and applies the 30-second limit to the whole `batch()` as well as individual queries. D1 automatically retries retryable read-only queries up to two additional times; application retries for transient writes must be bounded, exponential-with-jitter, and safe under the maintenance action's idempotency key. ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/), [D1 query retries](https://developers.cloudflare.com/d1/best-practices/retry-queries/))

Deployment remains bounded independently of runtime: the compressed Worker bundle limit is 3 MB on Free and 10 MB on Paid, with a 64 MB uncompressed limit and one-second startup limit. Cloudflare retains the latest 100 Worker versions for rollback, but a Worker rollback does not roll D1 data back. D1 migration application creates a backup; if one migration fails, that migration rolls back while earlier successful migrations remain applied. Treat schema rollout and Worker rollback as separate operations. ([Worker size and startup limits](https://developers.cloudflare.com/workers/platform/limits/), [Worker rollback limits](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/#limits), [D1 migration application](https://developers.cloudflare.com/d1/wrangler-commands/#d1-migrations-apply))

## Delivery, retry, overlap, and observability

- The Cron documentation does not promise exactly-once delivery, at-least-once delivery, automatic retry timing, or serialization against the next scheduled invocation. The current local test result exposes `noRetry`, and the pinned runtime type exposes `ScheduledController.noRetry()`, but no reviewed production documentation defines a retry contract for ordinary Cron Triggers. Do not make correctness depend on a provider retry or on `noRetry()`; persist application `next_due_at`, failure count, backoff/circuit state, leases, checkpoints, and idempotency keys in D1. ([local Cron result](https://developers.cloudflare.com/workers/configuration/cron-triggers/#test-cron-triggers-locally), [Workers types](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.122.0/packages/workers-types/index.d.ts))
- Cloudflare supports schedules as frequent as one minute while one invocation may run for 15 minutes, and it documents no non-overlap guarantee. Treat overlap as normal distributed-system behavior: acquire a conditional durable lease, skip a currently leased unit, and reclaim only after lease expiry. This is an implementation inference from the documented scheduling/duration surface, not a claim that overlap was observed in production. ([Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/), [Workers limits](https://developers.cloudflare.com/workers/platform/limits/))
- Cron Events keeps the 100 most recent scheduled invocations; a new or renamed Worker's events may take up to 30 minutes to appear. Workers Logs records Cron invocations, custom logs, errors, CPU time, and wall time; Worker metrics expose outcomes, subrequests, CPU, wall time, duration, and memory. D1 query results expose exact rows read/written, and D1 dashboard/GraphQL metrics provide longer aggregation. Use generated run correlation ID, job key, sanitized outcome/duration/counts, and D1 metadata only. Never log a source URL/query, fetched headers/body, PII, tokens, account IDs, or raw exception/stack text. ([Cron Events](https://developers.cloudflare.com/workers/configuration/cron-triggers/#view-past-events), [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/), [Workers metrics](https://developers.cloudflare.com/workers/observability/metrics-and-analytics/), [D1 metrics](https://developers.cloudflare.com/d1/observability/metrics-analytics/))

## Outbound source-check policy

- New Worker `Request` objects default to `redirect: "follow"`, and automatic following forwards all headers even across hosts. Use `redirect: "manual"`, send no credentials/cookies, validate the exact approved HTTPS hostname and port before the first request and again before the one permitted same-policy redirect, and record further/permanent/cross-host redirects only as private review observations. Cancel unused bodies. This both prevents credential leakage and preserves the 32-request planning cap. ([Workers `Request`](https://developers.cloudflare.com/workers/runtime-apis/request/), [Workers limits](https://developers.cloudflare.com/workers/platform/limits/))
- Cloudflare sets no per-subrequest timeout, while the scheduled invocation can live for 15 minutes. Supply an `AbortController.signal`, arm a short application timeout inside the handler, classify abort separately, and cancel the body after timeout or a terminal status. The runtime supports `AbortController`/`AbortSignal` and cancellation through `Request.signal`. ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Workers web standards](https://developers.cloudflare.com/workers/runtime-apis/web-standards/), [Workers `Request`](https://developers.cloudflare.com/workers/runtime-apis/request/))
- Cloudflare enforces no response-body maximum and an isolate has 128 MB memory; buffering an untrusted response can fail with `Memory limit would be exceeded before EOF`. Reject an over-budget declared length, then enforce the same per-source and per-run byte ceilings while streaming because `Content-Length` may be absent or wrong. Hash only bytes inside that finite policy and immediately discard/cancel the stream; never call unbounded `text()`/`arrayBuffer()` or store response bytes. ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Workers streaming guidance](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/#stream-request-and-response-bodies))
- Global Worker `fetch()` accepts public HTTP(S) URLs but does not support direct IP-literal fetches; private-service access is a separate VPC binding capability. Slice 9 has no VPC binding. Reject IP literals, `localhost`, userinfo, non-HTTPS schemes, unexpected ports, and unapproved hosts syntactically before every request. Enforce port 443 explicitly because current compatibility behavior permits outbound custom ports. Treat platform restrictions as defense in depth, not as the application's SSRF policy or a guarantee about a hostname's future DNS answer. ([Workers known issues](https://developers.cloudflare.com/workers/platform/known-issues/#fetch-to-ip-addresses), [custom outbound ports](https://developers.cloudflare.com/workers/configuration/compatibility-flags/#allow-fetching-to-custom-ports), [Workers VPC binding](https://developers.cloudflare.com/workers-vpc/api/))

## Native failure notification and privacy conclusion

Workers Logs are included on Free and Paid plans: Free includes 200,000 events/day with three-day retention; Paid includes 20 million/month with seven-day retention and charges for additional events. Logs are stored in the Cloudflare account, so sanitized logging is a privacy boundary, not merely presentation hygiene. Automatic traces capture outbound-fetch request metadata and are unnecessary for this source monitor; do not enable/export them without a separate privacy review. ([Workers Logs pricing](https://developers.cloudflare.com/workers/observability/logs/workers-logs/#pricing), [Workers traces](https://developers.cloudflare.com/workers/observability/traces/))

Cloudflare Notifications supports email delivery on Free accounts, but the official available-notifications catalog does not publish a Workers-script or Cron-failure type. The webhook schema names `workers_alert` and `workers_observability_alert`, but the reviewed public documentation does not establish their plan eligibility, pricing, setup, or Cron-failure semantics. Therefore no account-independent, no-cost native Cron/Worker failure email is verified for this slice, and none should be claimed or enabled from repository code. Rely on Cron Events, Workers Logs/metrics, and private coalesced D1 Automation Alerts. During an authenticated production rollout, the Operator may inspect the account-specific `available_alerts` result/dashboard; enable a provider email only if it exposes a relevant no-cost policy and its sample payload contains no private source or application data, then record that evidence in QA. Policy names, descriptions, identifiers, and exception summaries add provider-visible privacy surface and must omit source URLs and run details. General Cloudflare email availability is not evidence that such a Worker policy exists. ([Cloudflare Notifications plans](https://developers.cloudflare.com/notifications/), [available notifications](https://developers.cloudflare.com/notifications/notification-available/), [webhook payload schema](https://developers.cloudflare.com/notifications/reference/webhook-payload-schema/), [Alerting API](https://developers.cloudflare.com/api/resources/alerting/))

## Evidence boundary

This note verifies documentation, pinned package behavior, local counts, and planning arithmetic only. It does not prove a production D1 binding, deployed trigger, non-overlap, CPU fit, external-source behavior, provider alert, or successful scheduled run. Production QA must wait through trigger propagation and capture at least two real scheduled outcomes plus redacted Cron/Workers/D1 metrics before claiming autonomous operation.
